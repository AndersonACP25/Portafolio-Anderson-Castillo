PROFESSIONAL CASE STUDY

Regression testing: from 10 days to 5

Module-based automation helped a two-person QA team complete regression across more than 120 application pages while continuing to test sprint work.

10 daysBefore: manual regression
5 daysAfter: combined regression
50%Less regression time
Read the case study

Context & challenge

A mobile device management application supported regular and promotional pricing, bundles and bonuses across providers and branches. Regression required manual checks across more than 120 pages, including browser DevTools, API requests/responses and database validation.

The ten-day regression ran alongside the sprint, affecting production release schedules and leaving less time for QA tasks, test case preparation and user story validation documents.

My contribution

Within a team of two QA professionals, I took on most of the framework design and implementation using Playwright and TypeScript, including classes, interfaces, page objects and test data.

Strategy & implementation

  1. Start with the application core: prepare mobile devices so they were active and enabled for price generation before running dependent scenarios.
  2. Separate each window into selectors, test data, page interaction logic and test specifications. Run tests by module through package.json scripts.
  3. Handle Angular modals and ng-select components with reusable helpers/utilities, waits for parent and option components, input-state checks and tracking of whether the selector was expanded. Use try-catch handling for interaction errors.
  4. Check executions locally with the Playwright VS Code extension and reports. Investigate failures manually: report confirmed application defects in Azure DevOps; otherwise correct the automated test.

Result & remaining manual coverage

The complete regression cycle decreased from ten to five days while continuing to cover all application windows. This improvement was observed in successive regression cycles. Some modules that previously required hours could be executed in minutes.

The five-day cycle combined automated execution, manual validation and failure review. Critical core behavior and new sprint functionality that had not yet been automated continued to receive manual testing.

What I learned

I learned to structure a maintainable automation project and would strengthen my Node.js foundations earlier before starting a similar implementation.

CASE STUDY · DATA VALIDATION

Reusable SQL: from scattered checks to a shared Wiki

I built and documented a reusable query catalogue so QA, developers and the Product Owner could retrieve the data needed for recurring use cases without rebuilding each query from scratch.

Before: scattered investigation

Multiple application tabs and endpoint responses had to be compared to find the required values.

After: a reusable team reference

A shared Azure DevOps Wiki documented queries, their purpose, usage conditions and alternatives.

Explore the SQL case study

Context & recurring problem

The application had more than 120 pages and many related database tables. Data validation across maintenance screens required joins, filtering, grouping and ordering. Working in SQL Server Management Studio (SSMS), I needed to retrieve related values more directly instead of repeatedly comparing screens and API responses.

Building the query catalogue

  1. For each maintenance screen, identify the base table and its relationships, using my knowledge of the application flow. This investigation and documentation took several weeks.
  2. Combine JOIN and WHERE clauses with GROUP BY, HAVING and ORDER BY as required by the use case, so the result presented the values needed for validation.
  3. Test queries locally before publishing. Split long queries into smaller parts, check each part, then add joins progressively and verify that the returned data and WHERE conditions matched the intended scenario.
  4. Publish each query in the Azure DevOps Wiki with a short explanation of why it existed, the specific cases where it applied and alternatives. Team members could access and update the documentation.
  5. Document stored procedures used within specific workflows so their execution context was available alongside the queries.

Observed impact

The catalogue supported user story validation, certification testing, regression and production release activities. It reduced the need to recreate queries and made recurring data lookups more accessible to QA, developers and the Product Owner.

This was a qualitative improvement in reuse and access to knowledge; I did not record a time-saving percentage or database performance benchmark.

What this work demonstrates

Investigating table relationships, checking intermediate results and documenting query intent turned individual troubleshooting into a shared team resource. Reuse was supported by understanding when a query applied, rather than treating every query as interchangeable.

The Wiki and queries are internal. This anonymized account describes the method and observed benefits without publishing table names, records or execution instructions.
